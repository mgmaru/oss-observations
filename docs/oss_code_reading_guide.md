# OSS・他人のコードを読む方法 ― ジュニアエンジニア向けコードリーディングガイド

## はじめに

OSS（Open Source Software）や他人が書いたコードを読むとき、

> 「どこから読めばいいのかわからない」  
> 「ファイルが多すぎて途中で迷子になる」  
> 「上から読んでいるのに全体像がつかめない」

ということがよくあります。

コードリーディングで大切なのは、**コードを最初から最後まで読むことではありません。**

特に重要なのは、次の考え方です。

> **横に読むのではなく、1つの問い・ユースケースに沿って縦に読む。**

つまり、ファイル単位で全部読むのではなく、

**「この機能は、入口から結果までどう処理されるのか？」**

という1本の流れを追います。

---

# 1. 「横に読む」と「縦に読む」

## 横に読む

例えば次のような読み方です。

```text
file1.go を最初から最後まで読む
        ↓
file2.go を最初から最後まで読む
        ↓
file3.go を最初から最後まで読む
        ↓
...
```

この方法では、コード量が増えるほど情報量も増えます。

その結果、

- 何のためにこの関数を読んでいるのかわからなくなる
- 関係のない処理まで理解しようとしてしまう
- 全体像を掴む前に疲れる
- 読んだ内容を忘れてしまう

という問題が起こりやすくなります。

---

## 縦に読む

おすすめなのはこちらです。

```text
1つの問い・ユースケース
        ↓
公開API・入口
        ↓
主要な関数
        ↓
データ構造
        ↓
内部処理
        ↓
エラー処理・境界条件
        ↓
テスト
        ↓
Issue / PR / Commit
```

例えば、

> 「URLパラメータはRouterからHandlerへどう渡されるのか？」

という問いなら、その処理に関係するコードだけを追います。

**コードベース全体を理解する必要はありません。**

---

# 2. コードリーディングの基本原則

## 原則1：最初に「問い」を決める

コードを開く前に、

> **今回、何を知りたいのか？**

を決めます。

### 悪い問い

```text
gjsonのコードを理解する
```

範囲が広すぎます。

### 良い問い

```text
gjsonはグローバルな設定状態による
data raceをどのように解消したのか？
```

あるいは、

```text
URLパラメータはRouterからHandlerへどう渡されるのか？
```

```text
実装固有のエラーはどこで公開API向けのエラーへ変換されるのか？
```

などです。

**問いが具体的になるほど、読む必要のあるコードも少なくなります。**

---

# 3. おすすめの読む順番

## STEP 1：READMEを見る

最初に、そのOSSが何をするものなのか確認します。

見るポイントは次の程度で十分です。

| 見るもの | 確認すること |
|---|---|
| OSSの目的 | 何を解決するソフトウェアか |
| 使用例 | 利用者はどう使うのか |
| 公開API | 外部から何を呼び出すのか |
| 主要概念 | Router、Client、Resultなど |
| 制約 | 対応OS、バージョン、依存関係など |

ここでは**実装を細かく理解する必要はありません。**

目的は、

> 「このOSSは外から見ると何なのか」

を理解することです。

---

# 4. STEP 2：公開API・入口を探す

次に、処理の入口を探します。

Goであれば、例えば次のような関数が入口になりやすいです。

```go
New(...)
Get(...)
Parse(...)
Open(...)
Run(...)
ServeHTTP(...)
```

利用例が、

```go
result := gjson.Get(json, "user.name")
```

なら、まず見るのは `Get()` です。

```text
利用者
  │
  ▼
Get(...)
  │
  ▼
内部処理
```

**利用者側から内部へ入っていく**イメージです。

---

# 5. STEP 3：1本の処理経路を追う

入口を見つけたら、その機能に必要な処理だけを追います。

例えば、

```text
Get()
  ↓
parse()
  ↓
parseObject()
  ↓
Result生成
```

という経路があったとします。

このとき、

```text
別機能A
別機能B
最適化処理C
補助処理D
```

まで全部読む必要はありません。

まずは、

> **1つの入力が、どのように結果まで到達するのか**

を理解します。

---

# 6. STEP 4：重要なデータ構造を見る

関数だけでなく、データ構造にも注目します。

例えば、

```go
type Result struct {
    Type Type
    Raw  string
    Str  string
    Num  float64
}
```

という構造体があれば、

> 「このOSSは処理結果を `Result` という形で表現している」

と理解できます。

## 特に見るとよいもの

- `struct`
- `interface`
- enum相当の型
- `map`
- 設定オブジェクト
- context
- 状態を保持するフィールド

---

## なぜデータ構造が重要なのか

ソフトウェア設計では、

> **何をどのデータ構造で表現するか**

が非常に重要だからです。

```text
入力
 ↓
データ構造
 ↓
処理
 ↓
別のデータ構造
 ↓
出力
```

関数を追うだけでなく、

**「データがどの形で受け渡されているか」**

を見ると設計が理解しやすくなります。

---

# 7. STEP 5：テストを見る

OSSを読むとき、**テストは非常に重要なドキュメント**です。

実装コードだけでは、

> 「この挙動は意図したものなのか？」

が判断できないことがあります。

テストを見ると、

```text
入力
 ↓
処理
 ↓
期待する結果
```

が明確になります。

## 特に確認したいテスト

| 種類 | 見る理由 |
|---|---|
| 正常系 | 基本的な使い方がわかる |
| 異常系 | エラー設計がわかる |
| 境界値 | 仕様の境界がわかる |
| Regression Test | 過去に発生したバグがわかる |
| 並行処理テスト | thread safetyなどがわかる |

### テストは「実行可能な仕様書」

と考えることもできます。

---

# 8. STEP 6：Issue・PR・Commitを見る

コードを見ると、

> 「何をしているか」

は分かります。

しかし、

> **「なぜそうしたのか」**

はコードだけでは分からないことがあります。

そこで役に立つのが、

- Issue
- Pull Request
- Commit message
- Discussion
- Changelog

です。

---

## 例：data raceの修正

コードだけを見ると、

```go
var disabled atomic.Bool
```

となっているだけかもしれません。

しかし履歴を追うと、

```text
グローバル変数を使用
        ↓
並行アクセス
        ↓
data raceが発生
        ↓
Issueが報告される
        ↓
設計を変更
        ↓
atomic.Boolを採用
```

という設計判断の背景が見えてきます。

**実装を見るだけでなく、「なぜその実装になったのか」を調べることがOSS観察では重要です。**

---

# 9. 関係ないコードはブラックボックスにする

コードを読んでいると、知らない関数が次々に出てきます。

例えば、

```go
func parseSomething(...)
```

を見つけたとします。

ここで毎回中身を読んでしまうと、

```text
関数A
 ↓
関数B
 ↓
関数C
 ↓
関数D
 ↓
関数E
 ↓
...
```

とどんどん深く入り込みます。

これが**コードリーディングで迷子になる典型的な原因**です。

---

## 判断する

```text
                この関数は
           今回の問いに必要か？
              /          \
            Yes           No
             │             │
             ▼             ▼
          中を見る      ブラックボックス
```

例えば、

> 「JSON解析内部の処理」

程度に理解しておけば十分な場合もあります。

**今の問いに必要になるまで、内部を読まない。**

これは非常に重要です。

---

# 10. 「全部理解する」を目標にしない

大規模なOSSでは、コードベース全体を理解することは簡単ではありません。

そこで目標を、

```text
このOSSを全部理解する
```

ではなく、

```text
このOSSでは、この問題を
どのような設計で解決しているのか理解する
```

に変えます。

例えば、

```text
CORSのpreflight requestを
どの層で処理しているのか
```

だけでも十分な観察になります。

---

# 11. コードリーディングで便利な機能・コマンド

## Go to Definition

関数や型の定義へ移動します。

```text
Get()
 ↓
定義へ移動
```

IDEやVS Codeでは基本的な機能です。

---

## Find References

その関数・変数が、

> **どこから使われているか**

を調べます。

例えば、

```go
SetEscapeHTML
```

を調べれば、

```text
どこから呼ばれる？
どのテストで使用される？
どのコードに影響する？
```

を確認できます。

---

## Call Hierarchy

関数の呼び出し関係を確認します。

```text
Caller
  ↓
Function
  ↓
Callee
```

処理の流れを縦に追うときに便利です。

---

# 12. Gitを使って「歴史」を読む

## git blame

```bash
git blame path/to/file.go
```

そのコードが、

- 誰によって
- いつ
- どのCommitで

変更されたのか確認できます。

そこからCommitやPRへ移動します。

---

## git log -S

ある文字列が、

> **いつ追加・削除されたのか**

を探せます。

```bash
git log -S "DisableEscapeHTML"
```

例えば、

```text
DisableEscapeHTML
        ↓
いつ追加された？
        ↓
いつ変更された？
        ↓
なぜ変更された？
```

と歴史を追うことができます。

---

# 13. おすすめの調査ループ

OSSを観察するときは、次のループが便利です。

```text
      問いを決める
           │
           ▼
      公開APIを見る
           │
           ▼
      関数を1本追う
           │
           ▼
      データ構造を見る
           │
           ▼
       テストを見る
           │
           ▼
 Find References / git blame
           │
           ▼
    Issue / PR / Commit
           │
           ▼
 「なぜ？」を自分の言葉で説明
```

これを繰り返します。

---

# 14. コードを読む3つのレベル

コードリーディングでは、理解のレベルを分けて考えると便利です。

## Level 1：What

> **何をしているか？**

```text
この関数はJSONから値を取得する
```

---

## Level 2：How

> **どのように実現しているか？**

```text
pathを解析
 ↓
JSONを探索
 ↓
Resultを生成
```

---

## Level 3：Why

> **なぜこの設計なのか？**

```text
なぜmapではなくstructなのか？

なぜmutexなのか？

なぜ公開APIと内部関数を分けたのか？

なぜ既存APIを削除せずDeprecatedにしたのか？
```

OSS観察では、最終的に**Level 3の「Why」まで到達できると非常に学びが大きい**です。

---

# 15. 初心者がやりがちな読み方

| 読み方 | 問題 |
|---|---|
| ファイルを上から全部読む | 関係のないコードまで読む |
| 全関数を理解しようとする | 情報量が多すぎる |
| いきなり内部実装を見る | 全体像がない |
| テストを読まない | 期待される挙動がわからない |
| Git履歴を見ない | 設計理由がわからない |
| わからない関数を全部深掘りする | 迷子になる |
| OSS全体を理解しようとする | ゴールが大きすぎる |

---

# 16. おすすめの読み方

一方で、おすすめは次の方法です。

| 順番 | やること |
|---|---|
| 1 | **問いを1つ決める** |
| 2 | READMEで概要を知る |
| 3 | 公開API・入口を探す |
| 4 | **1本のユースケースを縦に追う** |
| 5 | 重要なデータ構造を見る |
| 6 | テストで期待する挙動を確認する |
| 7 | Find Referencesで利用箇所を見る |
| 8 | Issue / PR / Commitで設計理由を見る |
| 9 | 自分の言葉で説明する |

---

# 17. 具体例：tidwall/gjsonを読む

今回の観察テーマを例にします。

## 問い

> **gjsonは、グローバルな設定状態によるdata raceをどのように解消し、既存APIとの互換性をどう維持したか？**

---

## 読む対象

例えば、次のようなキーワードから始めます。

```text
DisableEscapeHTML
DisableModifiers
SetEscapeHTML
AddModifier
atomic.Bool
sync.RWMutex
```

---

## 読む流れ

```text
DisableEscapeHTML
        │
        ▼
どこから参照される？
        │
        ▼
Find References
        │
        ▼
従来のグローバル状態
        │
        ▼
なぜ問題になった？
        │
        ▼
Issue / Commit
        │
        ▼
SetEscapeHTML()
        │
        ▼
atomic.Bool
        │
        ▼
関連テスト
        │
        ▼
互換性はどう維持した？
        │
        ▼
Deprecated API
```

このように、

**「gjson.goを全部読む」のではなく、問いに必要な線だけを通る**

のがポイントです。

---

# 18. 90分でOSSを読むなら

例えば次のように時間を区切れます。

| 時間 | 内容 |
|---:|---|
| 0〜10分 | README・問い・対象範囲を確認 |
| 10〜25分 | 公開API・関連する型を確認 |
| 25〜50分 | 主要な処理経路を縦に追う |
| 50〜65分 | テストを見る |
| 65〜80分 | Issue・PR・Commitを見る |
| 80〜90分 | 学び・未確認事項を記録 |

**時間切れになったら終了することも重要です。**

OSSにはいくらでも深掘りできる場所があります。

そのため、

```text
理解できるまで読む
```

ではなく、

```text
決めた時間の中で
問いにどこまで答えられたか記録する
```

という考え方の方が継続しやすくなります。

---

# 19. 最終的なゴール

コードリーディングのゴールは、

> **コードを全部読んだこと**

ではありません。

目指したいのは、

> **「このOSSは、この問題を、この責務分割・データ構造・API設計で解決している」**

と自分の言葉で説明できることです。

例えば、

```text
問題
 ↓
どの層が責任を持つ？
 ↓
どんなデータ構造を使う？
 ↓
どんなAPIとして公開する？
 ↓
どのようにテストする？
 ↓
なぜこの設計になった？
```

まで説明できれば、そのコードから得た学びを自分の設計にも活かせます。

---

# まとめ

OSS・他人のコードを読むときに最も重要なのは、

> **横に読むのではなく、問い・ユースケースに沿って縦に読むこと**

です。

覚えておきたい流れは次の通りです。

```text
問い
 ↓
README
 ↓
公開API
 ↓
1本の処理経路
 ↓
データ構造
 ↓
テスト
 ↓
Issue / PR / Commit
 ↓
設計理由
 ↓
自分の言葉で説明
```

そして、もう1つ重要なのが、

> **今の問いに必要のないコードは、いったんブラックボックスとして扱うこと**

です。

**全部を理解しようとせず、1つの問題に対してコードがどう設計されているかを見る。**

この読み方を繰り返すことで、少しずつ大きなコードベースでも迷わず読めるようになります。
