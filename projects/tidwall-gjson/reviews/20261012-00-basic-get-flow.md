## 1. 内容の確認

### 「2265行目の `else` に入る？」は、事実として確定できる

`path = "user.name"` を当てはめると、各分岐は次のようになる。

| 行 | 条件 | 結果 |
| --- | --- | --- |
| 2178 | `len(path) > 1` | true |
| 2179 | `@`（modifier）または `!`（静的な値）で始まる | false → 2180〜2198は飛ばせる |
| 2200 | `[` または `{`（subselector）で始まる | false → 2201〜2258は飛ばせる |
| 2262 | `..`（JSON Lines）で始まる | false → 2265の `else` に入る |
| 2267 | `json[0] == '{'` | true → 2269の `parseObject(c, 1, "user.name")` |

「？」を外して書ける。また、メモの中で「特殊な修飾子」と「特殊な演算子」という2つの言い方が混ざっている。分岐ごとに、上の表の名前で書き分けると正確になる。

### 見落としている事実：2285行目の `return c.value`

`Get` が返すのは、parse関数の戻り値ではなく `c.value`。つまり `parseContext` は、結果の書き込み先としても使われている。`parseContext` についての疑問に直結するので、メモに加える。

### [疑問] parseContextを複数の関数で書き換えている

- 2269行目と2274行目の呼び出しは、別々の分岐の中にある。どちらも直後に `break` するので、1回の `Get` で呼ばれるのは片方だけ。
- `c` は、`Get` を呼ぶたびに2261行目で新しく作られる。ほかの呼び出しと共有されることはない。
- 実際に `c` を書き換えているのは `parseObject` の中。`c.value` や `c.piped` への代入を探すと、どの関数がどのフィールドを書くかを確かめられる。
- 「良くない気がした」理由（追いにくい、テストしにくい、など）を書いておくと、確かめられる問いに変えられる。例：「`parseObject` はなぜ結果を戻り値（`(int, bool)`）にせず、`c.value` に書くのか？」。答えを書く場合は、推測だと明記する。
- 2179行目の `modifiersAreDisabled` は、`c` と違ってパッケージ全体で共有される変数。呼び出しごとの状態と共有状態の違いとして、問い03・04につながる。

### 仮説1「jsonをParseする」との照合

`Get` を読んだ範囲でも、仮説1について言えることがある。JSON全体を先に解析する処理はない。`Get` は最初の `{` を探し、path と一緒に `parseObject` に渡しているだけ。`parseObject` が木を作るのか、文字列を順に走査するのかは、まだ確かめていない。

なお、`gjson.Parse`（507行目）はこの経路では呼ばれない。`Get` の中で呼ばれるのは、modifierの分岐（2197行目）だけ。仮説の「Parse」と混同しないよう気をつける。

### Type（enum）の節

- コードブロックの中の `// 0`〜`// 5` は、元のコードにはない。自分の注記だと明記する。行の範囲は30-44ではなく30-43（`Type` の定義自体は27-28行目）。
- 「取り違いを防ぐ」は推測。コードで確認できる利点は、46-63行目で `Type` に `String()` メソッドを定義していること。`int` のままではメソッドを付けられない。一方で、`r.Type == 3` のような型のない定数との比較はコンパイルが通る。防げるのは、`int` 型の変数との取り違えだけ。
- [疑問] `Type` という名前について：利用者のコードでは、`gjson.Type` や `gjson.String` のようにパッケージ名付きで見える。Goには、パッケージ名で修飾される前提で名前を短く付ける慣習がある。これと照らし合わせると、確かめられる問いになる。
- この節が今回の問いとどう関係するかも書く。`Alice` を返すとき `Result.Type` に何が入るかは、`parseObject` を読むと分かる。
